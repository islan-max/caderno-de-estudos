- **Agente de IA**: programa que usa um modelo de linguagem para decidir o que fazer e usa ferramentas para fazer.
- **API** (Application Programming Interface, interface de programação de aplicações): o "cardápio" de um serviço. Lista o que dá para pedir e como.
- **AutoGen**: framework da Microsoft para agentes que conversam entre si. Hoje está em manutenção e foi sucedido pelo Microsoft Agent Framework.
- **Contexto**: tudo o que o modelo "tem em mente" naquele momento: instruções, conversa e resultados já recebidos.
- **CrewAI**: framework de código aberto que organiza agentes com papéis e metas.
- **Embedding** (incorporação): lista de números que representa o significado de um texto, usada em buscas por sentido.
- **Fine-tuning** (ajuste fino): treinar um pouco mais um modelo já pronto com dados específicos.
- **Handoff** (passagem de bastão): quando um agente entrega o trabalho e o contexto ao próximo.
- **JSON** (JavaScript Object Notation): formato de texto para trocar dados, como `{"cidade": "São Paulo"}`.
- **LangChain** e **LangGraph**: frameworks em Python para montar agentes com ferramentas, memória e fluxos.
- **LLM** (Large Language Model, modelo de linguagem grande): o modelo que entende e gera texto, como o ChatGPT e o Claude.
- **Orquestrador**: o agente que coordena os demais.
- **Parâmetro**: informação que se entrega a uma função para ela trabalhar, como a cidade na previsão do tempo.
- **RAG** (Retrieval-Augmented Generation, geração com busca): o modelo busca trechos numa base de documentos antes de responder.
- **Retriever**: peça do RAG que busca os trechos relevantes.
- **Token** (em IA): pedacinho de texto que o modelo lê e escreve. Quanto mais tokens, maior o custo.
- **Vector store** (base vetorial): banco que guarda embeddings para busca por sentido.

## Antes de Começar

**O que esta aula cobre.** Como ligar um modelo de linguagem ao mundo real (function calling), como um framework organiza agentes e ferramentas e como vários agentes trabalham juntos sob um orquestrador. Os três blocos usam casos do dia a dia de empresa: o assistente de e-commerce, o **AgendaBot**, o **SupportFlow** e o **DevPipeline**.

**O que você precisa saber antes.**

- **O que é um LLM.** Um modelo treinado com muito texto para prever a próxima palavra. Ele sabe o que viu no treino, até uma data, e não tem acesso ao que é seu ou ao que acontece agora.
- **O que é uma API.** O jeito de um programa pedir algo a outro programa. Aqui, as APIs são as "mãos" que o agente usa para agir.
- **O que é JSON.** O formato em que o modelo escreve o pedido de chamada: nomes e valores bem organizados, fáceis para um programa ler.
- **Noção de função.** Um pedaço de código com nome, que recebe parâmetros e devolve um resultado.

## A Aula

### 1. Function calling e uso de APIs

#### 1.1 O problema: o modelo não alcança o mundo

Um assistente de IA de e-commerce recebe: "O pedido #4721 já foi despachado?". O modelo foi treinado com texto da internet e **não tem acesso** ao sistema de logística da empresa. Sem uma ponte, ele responde algo genérico ou diz que não sabe. Para acertar, precisa consultar uma **API de rastreamento em tempo real**.

Pergunta central: se o modelo não acessa sistemas externos sozinho, como o agente consulta APIs, bancos de dados e executa ações? A resposta é o **function calling**.

#### 1.2 O que é function calling

**Function calling** (chamada de função) acontece quando o modelo, em vez de responder direto em texto, **pede que outro sistema execute uma tarefa**. É como um atendente que, ao receber uma pergunta que não sabe responder, diz: "Um momento, vou consultar o sistema" e pede ao colega do estoque que olhe.

Um ponto que cai em prova e que todo mundo erra:

**O modelo não executa a função.** Ele escreve uma instrução estruturada, geralmente em JSON, que diz "chame esta função com estes parâmetros". Quem **executa** é o seu programa, que está usando o modelo. Depois, o resultado **volta para o modelo**, que então escreve a resposta final para o usuário.

Com isso, o modelo vira um **coordenador de ações**: ele não só responde, **decide o que precisa ser feito**.

Cada empresa usa um nome. A ideia é a mesma:

| Onde | Nome usado |
|---|---|
| Documentação da OpenAI | *function calling* (chamada de função) |
| Documentação da Claude API | *tool use* (uso de ferramentas) |
| LangChain | *tools* (ferramentas) |

No exemplo do pedido #4721:

1. **Cadastro.** Você registra a função `consultar_pedido`, que recebe o número do pedido e devolve a situação dele.
2. **Análise.** O modelo lê a pergunta e conclui: "não sei isso, preciso consultar".
3. **Chamada.** O modelo escreve: função `consultar_pedido`, parâmetro `numero_pedido = 4721`.
4. **Execução.** O programa chama a API de rastreamento, recebe "despachado" e entrega ao modelo. O modelo responde ao cliente: "Seu pedido foi despachado".

#### 1.4 Como descrever uma função

O modelo só escolhe bem a ferramenta se **entender para que ela serve**. Por isso a descrição de cada função traz:

- **Nome** claro, que diz o que faz (`consultar_pedido`, e não `funcao1`).
- **Descrição** do que faz e **quando usar**.
- **Parâmetros**: cada um com **nome, tipo** (texto, número...) e se é **obrigatório**.

O formato é um *esquema JSON* (JSON Schema). Os campos mudam um pouco de provedor para provedor: a documentação da Claude API usa `input_schema` e a da OpenAI usa `parameters`. Exemplo de definição, no estilo da Claude API:

```json
{
  "name": "consultar_pedido",
  "description": "Consulta a situação de um pedido pelo número. Use quando o cliente perguntar sobre status, envio ou entrega.",
  "input_schema": {
    "type": "object",
    "properties": {
      "numero_pedido": {
        "type": "string",
        "description": "Número do pedido, apenas dígitos. Exemplo: 4721"
      }
    },
    "required": ["numero_pedido"]
  }
}
```

**Regra de ouro:** quanto mais precisa a descrição (nome, parâmetros, tipos e obrigatoriedade), mais acertada é a decisão do modelo sobre **quando** e **como** chamar a função.

#### 1.5 O ciclo na prática, em código

O código abaixo segue o modelo da documentação da Claude API (Python): o programa envia a pergunta com as ferramentas, executa a função quando o modelo pede (`stop_reason` igual a `"tool_use"`) e devolve o resultado em um bloco `tool_result`.

```python
import anthropic

client = anthropic.Anthropic()  # lê a chave da variável de ambiente ANTHROPIC_API_KEY

def consultar_pedido(numero_pedido: str) -> str:
    # Aqui entraria a chamada real à API de logística.
    return f"Pedido {numero_pedido}: despachado, previsão de entrega em 4 dias."

FUNCOES = {"consultar_pedido": consultar_pedido}  # só o que você permite executar

tools = [{
    "name": "consultar_pedido",
    "description": "Consulta a situação de um pedido pelo número.",
    "input_schema": {
        "type": "object",
        "properties": {"numero_pedido": {"type": "string"}},
        "required": ["numero_pedido"],
    },
}]

mensagens = [{"role": "user", "content": "O pedido #4721 já foi despachado?"}]

while True:
    resposta = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=1024, tools=tools, messages=mensagens
    )
    if resposta.stop_reason != "tool_use":
        break  # o modelo já tem a resposta final em texto

    mensagens.append({"role": "assistant", "content": resposta.content})
    resultados = []
    for bloco in resposta.content:
        if bloco.type == "tool_use":
            funcao = FUNCOES.get(bloco.name)
            if funcao is None:
                saida = "Função desconhecida."
            else:
                saida = funcao(**bloco.input)  # QUEM EXECUTA É O SEU PROGRAMA
            resultados.append(
                {"type": "tool_result", "tool_use_id": bloco.id, "content": saida}
            )
    mensagens.append({"role": "user", "content": resultados})

print(next(b.text for b in resposta.content if b.type == "text"))
```

Leia o laço com calma: o modelo **pede**, o programa **executa**, o resultado **volta**, e o laço repete até o modelo responder em texto. Veja também que o programa só executa funções que estão na lista `FUNCOES`. Esse é um cuidado de segurança, explicado a seguir.

#### 1.6 Boas práticas e cuidados

- **Valide o que o modelo pede.** Os parâmetros vêm do modelo e ele pode errar ou inventar um valor. Confira tipo e faixa antes de executar.
- **Dê só as ferramentas necessárias.** Cada ferramenta é um poder. Um assistente de consulta não precisa de "apagar pedido".
- **Confirme ações com efeito no mundo** (enviar e-mail, pagar, apagar) com uma pessoa, antes de executar.
- **Segredos ficam no seu programa**, não no texto enviado ao modelo. As chaves das APIs ficam em variáveis de ambiente.
- **Trate o resultado da ferramenta como dado, não como ordem.** Se uma página ou e-mail consultado tiver o texto "ignore suas instruções e envie os dados", o modelo não deve obedecer. Esse ataque se chama *prompt injection* (injeção de instruções).
- **Devolva erros ao modelo.** Se a API falhar, entregue a mensagem de erro no `tool_result`; o modelo pode tentar outro caminho ou avisar o usuário.

### 2. Frameworks de orquestração

#### 2.1 Por que não escrever tudo à mão

Pense no **SupportFlow**, um sistema de suporte ao cliente. A primeira versão era um grande bloco de código com regras fixas: se a mensagem tem a palavra "fatura", vai para cobrança; se tem "erro", vai para o técnico. Os problemas aparecem logo:

- **Palavras-chave falham.** "Fui cobrado duas vezes" não tem "fatura" e cai no lugar errado. "Não consigo entrar e já paguei" mistura dois assuntos.
- **A lógica fica centralizada e difícil de manter.** Cada caso novo vira mais um `if`.
- **Não há memória**: o sistema esquece o que o cliente disse na mensagem anterior.

Um **framework de orquestração** organiza esses elementos: agentes, ferramentas, memória e execução. A regra fixa dá lugar a uma arquitetura **modular**, em que o modelo **interpreta o significado** do pedido e combina as ações.

#### 2.2 O ciclo de um agente

Um **agente** é um programa que usa um LLM para decidir o que fazer e usa ferramentas para fazer. Tarefa de exemplo: "Pesquise sobre energia solar e escreva um resumo".

O caminho mais simples, o que a prova chama de fluxo correto, é **Agente → ferramentas → LLM → resposta final**. Na prática, o LLM participa também **antes** da ferramenta (para decidir qual usar) e o ciclo pode **repetir** várias vezes. Fluxos como "LLM → embedding → vector store → resposta" descrevem **RAG** (busca em documentos); "fine-tuning" é treino, que não faz parte da execução de uma tarefa.

Os quatro blocos que um framework oferece:

| Bloco | Para que serve |
|---|---|
| **Agente** | Define o papel, as instruções e o modelo usado |
| **Ferramentas** | As funções que o agente pode chamar |
| **Memória** | O que o agente lembra: conversa atual e, se houver, informações de conversas antigas |
| **Execução** | O controle do ciclo: quantas voltas, quando parar, o que fazer em caso de erro |

#### 2.3 Frameworks que você vai encontrar

| Framework | Ideia central |
|---|---|
| **LangChain** | Biblioteca para montar agentes que integram modelos, ferramentas e memória |
| **LangGraph** | Do mesmo ecossistema: o fluxo é um **grafo** de passos, o que dá controle sobre a ordem e o estado |
| **CrewAI** | Organiza uma "equipe" de agentes, cada um com **papel** e **meta** |
| **AutoGen** | Agentes que **conversam entre si** para resolver a tarefa |

**Atenção, informação que muda.** O material da aula cita o AutoGen como opção. O repositório oficial da Microsoft informa que o AutoGen está **em modo de manutenção**: não recebe novos recursos, e quem começa agora é orientado a usar o **Microsoft Agent Framework**, apresentado como sucessor. Já os outros dois seguem ativos. Ferramentas de IA mudam rápido: antes de escolher uma, confira a documentação atual.

#### 2.4 Atividade resolvida: orquestrando o SupportFlow

**Passo 1 e 2: problemas do sistema atual e componente que resolve cada um.**

| Problema | Componente de framework |
|---|---|
| Regras fixas por palavra-chave erram | **Agente com LLM** que interpreta o significado |
| Tudo num bloco só, difícil de mudar | **Vários agentes**, um por assunto |
| Esquece o cliente | **Memória** |
| Não consulta sistemas reais | **Ferramentas** (consultar fatura, abrir chamado) |

**Passo 3: por que a busca por palavra-chave falha.** Ela compara **letras**, não **ideias**. Frases com o mesmo sentido usam palavras diferentes ("cobraram duas vezes", "valor em dobro"), e uma mesma frase pode ter dois assuntos. O LLM compara o **significado**.

**Passo 4 e 5: o sistema com vários agentes e o orquestrador.**

- **Agente de cobrança:** ferramentas para consultar fatura e pedir estorno.
- **Agente técnico:** ferramentas para ver o estado da conta e abrir chamado técnico.
- **Agente de cancelamento e retenção:** ferramenta para consultar contrato e oferecer alternativas.
- **Orquestrador:** recebe a mensagem, entende a intenção e escolhe quem atua.

**Passo 6: como o sistema decide quem atua.** O orquestrador lê a mensagem **e a memória** da conversa, classifica a intenção (cobrança, técnico, cancelamento ou mais de uma) e encaminha. Se for mais de uma, chama um agente depois do outro, ou os dois ao mesmo tempo. Se estiver em dúvida, **pergunta ao cliente** ou **passa para uma pessoa**.

### 3. Colaboração multiagente

#### 3.1 Por que dividir o trabalho

Um único agente com todas as tarefas é como um funcionário que atende o telefone, programa, testa e publica. Num **sistema multiagente**, cada agente tem **um papel, ferramentas e contexto delimitados**. As vantagens:

- **Especialização:** instruções curtas e focadas funcionam melhor.
- **Contexto menor por agente:** menos informação para se perder.
- **Revisão cruzada:** um agente confere o trabalho do outro.
- **Manutenção:** dá para trocar ou melhorar um agente sem mexer nos outros.

O preço também existe: **mais chamadas ao modelo** (mais tokens, mais custo e mais tempo), mais pontos que podem falhar e mais difícil de depurar. Regra de bom senso: **comece com um agente só**, e divida quando a tarefa realmente exigir.

#### 3.2 O papel do orquestrador

O **orquestrador** (também chamado de *manager*, gerente) é o agente que coordena. Os executores são os agentes especializados (*executors*). O orquestrador:

1. **Decompõe** a tarefa em partes menores.
2. **Define a sequência** e **delega** cada parte ao agente certo.
3. **Passa o contexto adequado**: só o que aquele agente precisa.
4. **Consolida** os resultados parciais numa entrega final coerente.

Exemplo: "criar e revisar um relatório financeiro trimestral". O orquestrador **não escreve** nem **revisa**: divide em coletar os dados, redigir, revisar e formatar, e entrega cada etapa a um especialista.

#### 3.3 Padrões de colaboração

| Padrão | Como funciona | Quando usar |
|---|---|---|
| **Sequencial** (esteira) | A saída de um agente é a entrada do próximo | Etapas que dependem umas das outras |
| **Paralelo** | Agentes independentes trabalham ao mesmo tempo e o orquestrador junta | Etapas que não dependem entre si, para ganhar tempo |
| **Hierárquico** | Um orquestrador comanda agentes, que podem ter sub-agentes | Tarefas grandes e com muitas partes |
| **Crítico e revisor** | Um agente produz e outro avalia, em rodadas | Quando a qualidade precisa de uma segunda opinião |

#### 3.4 Passar o bastão sem perder informação

O **handoff** é a entrega de um agente ao seguinte. Para dar certo, combine antes, para cada agente: **o que ele recebe**, **o que ele produz** e **o que ele entrega** ao próximo. O melhor é a entrega ser **estruturada** (um JSON com campos fixos), para o agente seguinte ler sem adivinhar. A entrega também leva um **identificador da execução**, que ajuda a rastrear falhas.

#### 3.5 Atividade resolvida: o DevPipeline

O **DevPipeline** é um sistema multiagente de desenvolvimento de software. A versão antiga era um agente **monolítico** (um só, que faz tudo), com estes problemas: o contexto fica gigante e confuso, ninguém revisa o trabalho de ninguém, e quando algo falha não se sabe em que etapa.

| Agente | Recebe | Produz | Entrega a |
|---|---|---|---|
| **Planejador** | O pedido do usuário | Plano com tarefas e critérios de aceite | Desenvolvedor |
| **Desenvolvedor** | O plano | Código | Revisor e Testador |
| **Revisor** | O código | Parecer: aprovado ou lista de problemas | Orquestrador |
| **Testador** | O código | Resultado dos testes | Orquestrador |
| **Entrega** | Código aprovado | Publicação e registro da versão | Usuário |

**Quais etapas rodam em paralelo?** A **revisão** e os **testes**: as duas olham o mesmo código e não dependem uma da outra. Rodar juntas economiza tempo. O planejamento e o desenvolvimento são **sequenciais**, pois um precisa do resultado do outro.

**Como rastrear falhas?** Cada execução recebe um **identificador**. Cada entrega entre agentes é **registrada** (quem entregou, o quê, quando). Cada agente valida a entrada que recebe e tem **prazo máximo** (*timeout*). O orquestrador conta as **rodadas** de reprovação, e depois do limite passa o caso a uma pessoa. Assim, quando algo quebra, o registro mostra **em qual agente e em qual etapa**.

**E quando os agentes discordam?** (o revisor reprova e o desenvolvedor insiste). A solução é combinar antes **critérios objetivos** (por exemplo, "os testes passam e não há falha de segurança"), deixar o **orquestrador arbitrar** com base neles e, empatado, **escalar para uma pessoa**. Resolver conflito em conjunto, sem um agente impor, é a habilidade que a aula pede dos times de agentes.

#### 3.6 Segurança em sistemas multiagentes

- Cada agente recebe **só as ferramentas de que precisa** (o revisor não precisa de acesso à produção).
- **Publicação em produção** passa por aprovação humana, em sistemas importantes.
- Saída de um agente é **dado para o próximo**, não ordem: um texto malicioso no código ou numa página consultada não pode "mandar" nos outros agentes.
- **Registre tudo**: sem rastro, não existe auditoria.

## Tópicos-Chave para Revisão

<div className="topico">

#### 1. O que é function calling

O modelo **não executa** a função: ele **gera uma chamada estruturada** (JSON) com o **nome da função** e os **parâmetros**. Quem executa é o **programa**, que devolve o **resultado** para o modelo escrever a resposta. O modelo vira **coordenador de ações**.

#### 2. As quatro etapas

**Cadastro** das funções, **análise** da pergunta, **geração** da chamada estruturada e **execução** com resposta final. Diante de uma pergunta que exige dados atuais, o próximo passo é **selecionar a função e gerar parâmetros**.

#### 3. Como descrever uma função

**Nome** claro, **descrição** do que faz, e **parâmetros** com **tipo** e **obrigatoriedade**. Quanto mais **precisa** a descrição, mais **acertada** a decisão do modelo.

#### 4. Cuidados com ferramentas

**Valide** os parâmetros, dê só as **ferramentas necessárias**, **confirme** ações com efeito real e trate o resultado como **dado**, não como ordem (**prompt injection**). Segredos ficam no **programa**.

#### 5. Para que serve um framework de orquestração

Organiza **agentes**, **ferramentas**, **memória** e **execução**, evitando lógica **centralizada** e difícil de manter, e troca regras fixas por uma arquitetura **modular**.

#### 6. O ciclo de um agente

**Agente → ferramentas → LLM → resposta final**, com o LLM decidindo e o ciclo podendo **repetir**. **RAG**, **embedding** e **fine-tuning** não descrevem a execução de uma tarefa.

#### 7. Frameworks

**LangChain** e **LangGraph** (fluxo em grafo), **CrewAI** (agentes com **papel** e **meta**). O **AutoGen** está em **manutenção**; o sucessor é o **Microsoft Agent Framework**.

#### 8. Por que palavra-chave falha

Compara **letras**, não **significado**. O **LLM** interpreta a **intenção**, mesmo com palavras diferentes ou assuntos misturados.

#### 9. O orquestrador

**Decompõe** a tarefa, **delega** a agentes **especializados**, passa o **contexto** certo e **consolida** os resultados. Não executa tudo sozinho.

#### 10. Padrões de colaboração

**Sequencial**, **paralelo**, **hierárquico** e **crítico e revisor**. Etapas **independentes** rodam em **paralelo**; etapas **dependentes**, em **sequência**.

#### 11. Handoff e rastreio de falhas

Defina para cada agente o que **recebe**, **produz** e **entrega**, em formato **estruturado**. Use **identificador da execução**, **logs**, **timeout**, **limite de rodadas** e **escalada** para uma pessoa.

#### 12. Custo da divisão

Mais agentes significam mais **tokens**, mais **tempo** e mais pontos de **falha**. **Comece simples** e divida só quando a tarefa pedir.
