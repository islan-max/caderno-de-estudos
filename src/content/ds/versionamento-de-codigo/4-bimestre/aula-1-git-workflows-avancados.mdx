<Accordion titulo="Palavras e siglas desta aula" dica="Consulte quando encontrar um termo novo" icone="spell-check">

- **Git**: sistema que guarda o histórico do código e permite que várias pessoas trabalhem no mesmo projeto.
- **Repositório**: a pasta do projeto com todo o histórico do Git.
- **Commit**: um "ponto de salvamento" no histórico, com uma descrição da mudança.
- **Branch** (ramo): uma linha separada de trabalho, que sai do projeto principal.
- **Merge** (mesclagem): juntar as mudanças de uma branch em outra.
- **Conflito de merge**: acontece quando duas branches mudaram o mesmo trecho e o Git não sabe qual versão manter.
- **Main** (ou trunk, tronco): a branch principal, que representa a versão "oficial" do projeto.
- **Workflow** (fluxo de trabalho): o combinado da equipe sobre como usar branches e merges.
- **GitFlow**: workflow com branches fixas: main, develop, feature, release e hotfix.
- **Trunk-Based Development** (desenvolvimento baseado em tronco): workflow em que todos integram mudanças pequenas e frequentes na branch principal.
- **Hotfix**: correção urgente de um erro que já está em produção.
- **Release** (versão): o pacote que será entregue aos usuários.
- **Tag**: um rótulo, como "v1.0.0", colado a um commit para marcar uma versão.
- **Feature flag** (sinalizador de recurso): um interruptor no código que liga ou desliga uma funcionalidade sem novo deploy.
- **CI** (Continuous Integration, integração contínua): rotina automática que junta, constrói e testa o código a cada mudança.
- **CD** (Continuous Delivery, entrega contínua): manter o projeto sempre pronto para ser publicado.
- **Lead time**: o tempo entre começar uma mudança e ela chegar aos usuários.
- **Pull Request (PR)**: pedido para juntar uma branch na principal, com revisão do time.
- **SemVer** (Semantic Versioning, versionamento semântico): numeração MAJOR.MINOR.PATCH, como 2.4.1.

## Antes de Começar

**O que esta aula cobre.** Três blocos: revisar o Git e entender **por que** workflows existem; ver o **GitFlow** na prática; e conhecer o **Trunk-Based Development** com as **feature flags**. No fim, o objetivo é **escolher e justificar** um workflow para uma equipe.

**O que você precisa saber antes.**

- **Os comandos básicos**: `git add`, `git commit`, `git branch`, `git merge`, `git push`.
- **A ideia de branch**: uma cópia "virtual" do projeto para trabalhar sem mexer na versão principal.
- **Testes automatizados e CI**: rotinas que verificam o código sozinhas (vistas nas semanas de integração contínua).

## A Aula

### 1. Revisão de Git e motivação para workflows

#### 1.1 O problema de juntar o trabalho no fim

Uma equipe desenvolve um site, e cada pessoa cuida de uma parte: **home, formulário, galeria e avisos**. Cada uma trabalha **sozinha**, e tudo funciona. Na hora de juntar, vêm os **erros, os conflitos** e as partes que não funcionam juntas.

O que a equipe poderia ter feito **desde o início**:

1. **Combinar um workflow** (como criar branches, quando juntar, quem revisa).
2. **Integrar cedo e com frequência**: juntar o trabalho todo dia (ou várias vezes ao dia), e não só no fim.
3. **Dividir em tarefas pequenas**, que podem ser entregues em pouco tempo.
4. **Revisar em Pull Requests** e **rodar testes automáticos** a cada junção.
5. **Combinar quem mexe em quê**, para evitar duas pessoas no mesmo arquivo ao mesmo tempo.

#### 1.2 Revisando o básico do Git

| Conceito | O que é |
|---|---|
| **Commit** | Registra uma mudança no histórico |
| **Branch** | Cria uma linha separada de trabalho |
| **Merge** | Junta as alterações de branches diferentes |
| **Repositório** | Armazena o histórico do projeto |

Esses elementos permitem que **várias pessoas trabalhem no mesmo projeto sem mexer em tudo ao mesmo tempo**. O ciclo básico, no dia a dia:

```bash
git switch -c feature/galeria      # cria e entra numa branch nova
git add .                          # separa as mudanças para o commit
git commit -m "Adiciona a galeria" # registra
git push -u origin feature/galeria # envia para o repositório remoto
git switch main                    # volta para a principal
git pull                           # traz as novidades dos colegas
git merge feature/galeria          # junta a feature na main
```

(O `git switch` é a forma moderna do antigo `git checkout` para trocar de branch.)

#### 1.3 Feature Branch Workflow (main + feature branches)

O jeito mais comum de começar: existe uma branch principal, a **main**, onde fica a versão "oficial". **Cada nova tarefa** é feita numa **branch separada** (`feature-login`, `feature-galeria`). Você desenvolve e testa a sua parte nela, **sem mexer direto** na main. Quando termina, a branch é **juntada (merge)** na main.

Funciona bem **no começo** e com equipes pequenas. O problema aparece quando as branches **demoram** a voltar para a main.

#### 1.4 O problema da integração tardia

A **integração tardia** acontece quando uma branch fica **muito tempo separada** da principal. Consequências:

- **Diferenças grandes** entre as branches.
- **Conflitos de merge mais difíceis**: duas pessoas mudaram os mesmos arquivos de formas diferentes.
- **Erros descobertos tarde**: só aparecem na hora de juntar.
- **Atraso** para colocar mudanças em produção.

Quanto **mais tempo** a branch fica isolada, **maior** tende a ser o risco de conflito e de retrabalho.

**Um exemplo de conflito.** Duas pessoas editaram a mesma linha. O Git marca o arquivo para você decidir:

```text
<<<<<<< HEAD
<h1>Bem-vindo à loja</h1>
=======
<h1>Olá! Conheça a loja</h1>
>>>>>>> feature/home
```

Você escolhe (ou combina) a versão certa, apaga as marcas e faz um novo commit. Um conflito pequeno se resolve em minutos. Um conflito entre duas branches que ficaram semanas isoladas pode tomar **um dia inteiro**.

**Como isso afeta a entrega contínua.** A entrega contínua depende de mudanças **pequenas, frequentes e fáceis de validar**. Com integração tardia:

- O **build** quebra com mais facilidade.
- Os **testes** acumulam problemas.
- O **feedback** demora.
- A entrega **perde ritmo**.

Por isso, workflows não servem apenas para organizar branches: eles determinam **a velocidade com que o time recebe feedback**.

#### 1.5 Os dois caminhos

Para reduzir esses problemas, equipes adotam um de dois grandes modelos:

- **GitFlow**: mais estrutura, com branches fixas e controle de versões.
- **Trunk-Based Development**: integração muito frequente numa branch só.

Os dois são válidos. A escolha depende do **tamanho da equipe**, do **nível de controle** necessário sobre as versões e da **frequência de entrega** desejada.

#### 1.6 Qual workflow escolher? Dois cenários

| | Cenário A | Cenário B |
|---|---|---|
| **Equipe** | Pequena, integra com frequência | Releases mais formais |
| **Testes** | Automatizados | Preparação de versão separada |
| **Entrega** | Várias versões por semana | Fluxo mais controlado, correções urgentes à parte |

1. **Qual combina com Trunk-Based Development?** O **A**: equipe pequena, integração frequente, testes automáticos e publicação várias vezes por semana.
2. **Qual combina com GitFlow?** O **B**: precisa separar a preparação de versão das correções urgentes, com fluxo controlado.
3. **Qual favorece mais a integração frequente?** O **A** (Trunk-Based).
4. **Em uma frase:** o Trunk-Based mantém tudo integrado o tempo todo, e o GitFlow troca velocidade por controle de versões.

### 2. Implementando GitFlow na prática

#### 2.1 As branches do GitFlow

O **GitFlow** foi descrito por Vincent Driessen em 2010. Ele usa **duas branches permanentes** e **três tipos de branches de apoio**:

| Branch | Para que serve | Nasce de | Volta para |
|---|---|---|---|
| **main** | Só o que foi **lançado**. Cada commit nela é uma versão, marcada com **tag** | (permanente) | (permanente) |
| **develop** | **Integração**: onde as funcionalidades prontas se juntam antes da release | (permanente) | (permanente) |
| **feature/…** | Uma funcionalidade nova | **develop** | **develop** |
| **release/…** | Prepara uma versão: só **correções finais** e número da versão, sem funcionalidade nova | **develop** | **main** e **develop** |
| **hotfix/…** | **Correção urgente** de um erro que está em produção | **main** | **main** e **develop** |

Resposta direta: **as funcionalidades prontas são integradas na `develop`**, antes de a release ser preparada. A `main` guarda só o que já foi lançado.

#### 2.2 O ciclo completo, passo a passo

Esta é a simulação do roteiro da aula, feita com comandos do próprio Git (o resultado foi testado numa pasta nova). Não precisa de nenhuma ferramenta extra.

**Passo 1: criar a base do projeto.**

```bash
git init -b main loja-gitflow
cd loja-gitflow
echo "# Loja" > README.md
git add .
git commit -m "Base do projeto"
git switch -c develop
```

**Passo 2: criar uma funcionalidade (feature) e integrá-la.**

```bash
git switch -c feature/carrinho develop
echo "carrinho" > carrinho.txt
git add .
git commit -m "Adiciona o carrinho"

git switch develop
git merge --no-ff feature/carrinho -m "Integra o carrinho"
git branch -d feature/carrinho
```

O `--no-ff` (sem *fast-forward*) **sempre cria um commit de merge**. Assim, o histórico mostra **quais commits formaram a feature**, e desfazer a funcionalidade inteira fica mais fácil.

**Passo 3: preparar a entrega (release).**

```bash
git switch -c release/1.0.0 develop
echo "1.0.0" > VERSAO
git add .
git commit -m "Prepara a versão 1.0.0"

git switch main
git merge --no-ff release/1.0.0 -m "Release 1.0.0"
git tag -a v1.0.0 -m "Versão 1.0.0"

git switch develop
git merge --no-ff release/1.0.0 -m "Volta da release 1.0.0 para a develop"
git branch -d release/1.0.0
```

Na release, **só entram correções finais**: nenhuma funcionalidade nova. Quando fica pronta, ela é juntada na **main** (com a **tag** da versão) **e** na **develop**, para que as correções finais não se percam.

**Passo 4: corrigir um erro em produção (hotfix).**

```bash
git switch -c hotfix/1.0.1 main
echo "1.0.1" > VERSAO
git add .
git commit -m "Corrige o erro de pagamento"

git switch main
git merge --no-ff hotfix/1.0.1 -m "Hotfix 1.0.1"
git tag -a v1.0.1 -m "Versão 1.0.1"

git switch develop
git merge --no-ff hotfix/1.0.1 -m "Hotfix 1.0.1 na develop"
git branch -d hotfix/1.0.1
```

O hotfix **nasce da main** (porque o erro está em produção, e não na develop) e **volta para os dois**. Se houver conflito no último merge, resolva como vimos na seção 1.4.

Para ver o resultado: `git log --oneline --graph --all --decorate`.

**Existe uma extensão `git flow`** que automatiza esses passos, mas ela não é necessária: os comandos acima fazem o mesmo, e entender cada um é melhor para aprender.

#### 2.3 Versões e tags

Cada release ganha um número. O padrão mais usado é o **SemVer**, com três números: **MAJOR.MINOR.PATCH** (por exemplo, 2.4.1).

- **PATCH** sobe quando você **corrige** um erro sem mudar o funcionamento (1.0.0 para 1.0.1, como no hotfix).
- **MINOR** sobe quando acrescenta uma funcionalidade **compatível** (1.0.1 para 1.1.0).
- **MAJOR** sobe quando muda algo que **quebra a compatibilidade** (1.1.0 para 2.0.0).

A **tag** (`v1.0.0`) marca exatamente o commit daquela versão, para você poder voltar a ele quando quiser.

#### 2.4 Quando usar o GitFlow, e quando não

**Vantagens:**

- **Controle de versões**: fica claro o que está em produção, o que está em preparação e o que está em desenvolvimento.
- Separa **desenvolvimento, correções e preparação** de entrega.
- Combina com **releases mais formais** e com manutenção **previsível**.

**Custos:**

- **Mais etapas e mais complexidade.**
- **Branches que vivem mais tempo**, o que leva de volta ao problema da integração tardia.
- **Merges extras** (a release e o hotfix voltam para dois lugares).

**Uma observação importante.** O próprio autor do GitFlow escreveu, em 2020, uma nota no artigo original: o modelo virou "padrão" e, às vezes, **dogma**, mas **aplicações web costumam ser entregues continuamente**, e para isso ele recomenda um fluxo **mais simples**, como o GitHub Flow. O GitFlow continua indicado para software **com versões explícitas** ou que precise **manter várias versões** ao mesmo tempo (um aplicativo instalado, uma biblioteca).

Em resumo: **o GitFlow não é "o certo"; é uma ferramenta para um tipo de projeto.**

#### 2.5 Nomes e hábitos que ajudam

- **Nomes claros**: `feature/carrinho`, `release/1.0.0`, `hotfix/1.0.1`.
- **Proteger** a `main` e a `develop` (ninguém commita direto: só por Pull Request, com revisão e testes).
- **Apagar** as branches de apoio depois do merge.
- **Registrar** as mudanças de cada release (um arquivo de changelog).

### 3. Trunk-Based Development e feature flags

#### 3.1 O que é o Trunk-Based Development

No **Trunk-Based Development** (desenvolvimento baseado em tronco), o time **integra mudanças pequenas e frequentes na branch principal**, o **tronco** (*trunk*). Em vez de manter branches separadas por muito tempo, o foco é **reduzir o tempo entre desenvolver e integrar**.

Como funciona na prática:

- Todos trabalham a partir do tronco.
- Se usar branches, elas são **curtas**: duram **horas**, no máximo alguns dias, e voltam para o tronco por Pull Request rápido.
- O tronco **precisa estar sempre funcionando**: por isso há **testes automáticos** e **CI** a cada mudança.
- As mudanças são **pequenas**, fáceis de revisar.

**O que esse modelo favorece:** **feedback rápido**, **menos conflito acumulado**, **entregas frequentes** e uma **integração contínua mais natural**.

**O que ele exige:** testes automatizados confiáveis, revisão de código rápida, hábito de dividir o trabalho em passos pequenos e uma maneira de **esconder o que ainda não está pronto**. É aí que entram as feature flags.

#### 3.2 Branches longas e o lead time

Uma **branch longa** é uma branch que passa **dias ou semanas** sem voltar ao tronco. Os riscos:

- **Mais conflito**: quanto mais tempo passa, mais coisas mudam no tronco.
- **Integração atrasada**: erros só aparecem no fim.
- **Revisão difícil**: um Pull Request gigante é cansativo, e as pessoas revisam por cima.
- **Lead time maior.** O **lead time** é o tempo entre começar uma mudança e ela chegar aos usuários. Branches longas **aumentam** esse tempo, porque a mudança fica "parada" esperando para ser integrada. Equipes que medem a velocidade de entrega costumam acompanhar o lead time.

#### 3.3 Feature flags

Se o trabalho é integrado todo dia, como lidar com uma funcionalidade que leva **três semanas** para ficar pronta? Sem solução, o time criaria uma branch longa. A solução é a **feature flag** (sinalizador de recurso), um **interruptor** no código:

- O código novo **entra no tronco** (integrado e testado com todo o resto), mas **desligado**.
- Quando a funcionalidade fica pronta, **liga-se a flag** e ela aparece para os usuários, **sem um novo deploy**.

```js
// Configuração das flags (pode vir de um arquivo, variável de ambiente ou serviço)
const flags = { novoCheckout: false };

function telaDeCheckout() {
  return flags.novoCheckout ? checkoutNovo() : checkoutAtual();
}
```

A prática recomendada por quem defende o Trunk-Based Development é concentrar a escolha em **um único ponto** (por exemplo, no início do programa), em vez de espalhar `if` por todo o código.

**O que a flag permite:**

- **Subir código sem expor** a funcionalidade, e **evitar branches longas** (o problema do quiz).
- **Lançamento gradual**: ligar para 5% dos usuários, depois 25%, depois todos.
- **Teste A/B**: mostrar versões diferentes para grupos diferentes e comparar.
- **Botão de emergência** (*kill switch*): desligar uma funcionalidade que deu problema, sem refazer o deploy.
- **Liberar para um grupo** (a equipe, usuários beta) antes dos demais.

**Cuidados:**

- **Dívida de flags.** Depois que a funcionalidade está liberada para todos, **remova a flag e o código antigo**. Flags esquecidas viram lixo e complicam a leitura. Combine uma data de revisão.
- **Teste os dois estados**: o código com a flag ligada **e** desligada. O código "desligado" também precisa estar testado.
- **Não é segurança.** Em aplicações de navegador, o usuário pode ver as flags no código. Nunca use flag para esconder dado sigiloso.
- **Não exagere**: muitas flags ao mesmo tempo geram combinações demais.

Existem serviços e bibliotecas prontos para gerenciar flags (como o Unleash, o LaunchDarkly e o padrão aberto OpenFeature), mas o princípio é simples e pode começar com uma variável de configuração.

#### 3.4 GitFlow ou Trunk-Based: comparação

| Critério | GitFlow | Trunk-Based Development |
|---|---|---|
| **Branches** | Várias, de vida longa (main, develop) e de apoio | Uma principal; as outras duram horas |
| **Integração** | Em etapas (feature, develop, release, main) | Contínua, no tronco |
| **Conflitos** | Tendem a ser maiores | Pequenos e frequentes |
| **Versões** | Muito controle, com release formal | A versão sai do tronco a qualquer hora |
| **Código incompleto** | Fica em branch de feature | Entra no tronco, atrás de **feature flag** |
| **Exige** | Disciplina com as branches | **Testes automáticos e CI** confiáveis |
| **Combina com** | Releases formais, várias versões, equipes grandes e processos de aprovação | Entrega contínua, produto web, times com bons testes |

**Como decidir.** Faça três perguntas:

1. **Com que frequência entregamos?** Várias vezes por semana pede Trunk-Based. Em versões fechadas e espaçadas, o GitFlow pesa menos.
2. **Temos testes automáticos confiáveis?** Sem eles, o tronco fica arriscado.
3. **Precisamos manter várias versões ao mesmo tempo?** Se sim, o GitFlow ajuda.

#### 3.5 Atividade resolvida: comparando os dois modelos

Situação: uma equipe de 5 pessoas faz uma loja virtual e publica toda semana. Uma funcionalidade de **cupom de desconto** levará 3 semanas. Eles usam GitFlow e as branches de feature estão demorando para ser integradas e causam muitos conflitos.

1. **Identifique o problema.** A **branch de feature longa**: ela fica semanas isolada e a integração atrasa. Com isso, os conflitos crescem e o feedback demora.
2. **Compare os modelos.** No GitFlow, a feature só entra na `develop` quando termina (semanas depois). No Trunk-Based, o código entraria no tronco aos poucos, desde o primeiro dia. Para uma equipe pequena que publica toda semana, o Trunk-Based encaixa melhor.
3. **Pense numa solução com feature flags.** Dividir o cupom em partes pequenas (cadastro do cupom, cálculo do desconto, tela de aplicação), integrar cada parte no tronco **atrás da flag `cupomDeDesconto` desligada** e ligar só quando tudo estiver pronto.
4. **Tome a decisão.** Adotar o Trunk-Based com feature flags e, como base, **testes automáticos e CI**. Registrar o motivo: "equipe pequena, publica toda semana, queremos menos conflitos".
5. **Cuidados.** Combinar a data para remover a flag e testar o fluxo com ela ligada e desligada.

## Tópicos-Chave para Revisão

<div className="topico">

#### 1. Por que existem workflows

Sem um combinado, as partes feitas **em separado** dão **conflito** e **erros** na hora de juntar. Um **workflow** define como usar **branches** e **merges** e favorece integrar **cedo e com frequência**.

#### 2. Básico do Git

**Commit** registra uma mudança, **branch** cria uma linha separada, **merge** junta e **repositório** guarda o histórico. O **git switch** troca de branch.

#### 3. Feature Branch Workflow

**main** é a versão oficial. Cada tarefa vai numa **feature branch** e volta para a main por **merge**. Funciona no começo, mas sofre com a **integração tardia**.

#### 4. Integração tardia

Branch **muito tempo isolada** gera **conflitos maiores**, **erros descobertos tarde** e **feedback lento**. Atrapalha a **entrega contínua**: o **build** quebra, os **testes** acumulam problemas.

#### 5. Branches do GitFlow

**main** (só o lançado, com **tag**), **develop** (**integração** das funcionalidades), **feature** (sai da develop), **release** (sai da develop, só correções) e **hotfix** (sai da main).

#### 6. Para onde cada uma volta

**feature** volta para a **develop**. **release** volta para a **main** e para a **develop**. **hotfix** volta para a **main** e para a **develop**. Use **merge --no-ff**.

#### 7. Versões

**SemVer**: **MAJOR.MINOR.PATCH**. Hotfix sobe o **PATCH**, funcionalidade compatível sobe o **MINOR**, mudança que quebra sobe o **MAJOR**. A **tag** marca o commit da versão.

#### 8. Quando usar o GitFlow

Bom para **releases formais**, **várias versões** e **manutenção previsível**. Custa **mais etapas e complexidade**. Para aplicações web com **entrega contínua**, o próprio autor recomenda algo **mais simples**.

#### 9. Trunk-Based Development

Mudanças **pequenas e frequentes** no **tronco**, com branches de **horas**. Dá **feedback rápido** e **menos conflito**, mas exige **testes automáticos** e **CI**.

#### 10. Lead time

Tempo entre **começar** uma mudança e ela **chegar ao usuário**. **Branches longas aumentam** o lead time e o risco de **conflito**.

#### 11. Feature flags

**Interruptor** que deixa o código entrar **desligado** no tronco e ser **ligado depois**, **sem novo deploy**. Evita **branches longas**. Cuidado com a **dívida de flags** e **teste os dois estados**.

#### 12. Escolher o workflow

Depende do **tamanho da equipe**, do **controle necessário** e da **frequência de entrega**. Equipe pequena que publica várias vezes por semana combina com **Trunk-Based**; releases formais combinam com **GitFlow**.
